# Local RAG review — 24 September 2026

Scope: LokLM's existing document/code retrieval, balanced speed and answer quality, a 4 GB GPU, and the user's requirement that inference must not silently fall back to CPU-only operation. This is a source/code review, not a new hardware benchmark. File references describe the starting implementation; concurrent fixes may move the lines.

## Decision

Keep the existing lexical + dense retrieval and source-cited answer pipeline. On a 4 GB GPU, skip the optional cross-encoder reranker, use the existing lighter retrieval path, and give the active model exclusive GPU residency when required. Show the reason and the selected model's actual capacity in Settings. A 4 GB GPU is constrained; that alone does not establish that the whole application is unusable.

Skipping reranking removes an additional passage-relevance judgment. It may reduce precision on ambiguous prose queries, while saving a model load and scoring pass; it does not remove document search or citations. This tradeoff follows the user's preference and the implementation's resource costs, not an assumption that reranking never helps. BEIR found BM25 robust and rerankers strong on average but computationally expensive across its tested datasets. Those results do not quantify this app's quality loss. [BEIR, original paper](https://arxiv.org/abs/2104.08663).

RRF was designed to combine ranked result lists without pretending their native scores are comparable. LokLM's BM25/dense approach is consistent with that rationale. [Cormack et al., original RRF paper](https://doi.org/10.1145/1571941.1572114).

BAAI recommends hybrid retrieval with optional precision improvement from reranking; its BGE-M3 query embedding needs no instruction prefix. Qwen3-Embedding supports task instructions and multilingual/code use. The current per-model query formatting should remain intact. [BGE-M3 official model card](https://huggingface.co/BAAI/bge-m3), [Qwen3-Embedding official model card](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B).

## Minimal changes now

1. **Enforce resource policy centrally.** A constrained GPU must not load the reranker through startup, Chat mounting, manual warmup, provider reload or direct ranking. A GPU-unavailable error should be actionable, not trigger CPU-only inference. Report GPU memory separately from system RAM; GGUF file size alone is not a fit estimate because weights, working buffers and context all consume memory.
2. **Use the real no-reranker path.** Initially `effectiveRerank` at `RetrievalService.ts:383` can be true while the provider is unavailable. The BM25 weight at `:470` and relevance floor at `:485` then omit fallback behavior even though no rerank occurs at `:545`. Resolve availability/policy before fusion. The renderer currently requests reranking at `src/renderer/src/chat/ChatView.tsx:325`; a UI preference alone cannot enforce this correctly.
3. **Record whether reranking actually succeeded.** `maybeRerank` at `RetrievalService.ts:875` catches a failure and returns fused scores, but the caller can still apply the cross-encoder threshold at `:624` and report a successful rerank. Track success separately; fused ranks and cross-encoder scores must not share a threshold. The official reranker card explains the distinct query/passage scoring stage. [BGE reranker official model card](https://huggingface.co/BAAI/bge-reranker-v2-m3).
4. **Apply the lighter path to hardware, not only install tier.** `src/main/index.ts:2118` already disables extra LLM query expansion, uses heuristic follow-up context and limits whole-document expansion for Lite. Standard/dev on a small GPU can otherwise retain the expensive path. Use measured hardware policy for the same conservative defaults while keeping an advanced, explicit quality choice where supportable.
5. **Explain the outcome in ordinary language.** Settings should say that enhanced reranking is unavailable on the detected GPU, hybrid search remains active, and a smaller chat model may run more responsively. If the selected model cannot run with supported GPU acceleration, surface that specific limitation before the user sends a message. Avoid treating partial GPU offload as full GPU fit.

These findings were handed to the GPU-policy implementation agent. The retrieval availability/success corrections in items 2–3 are implemented: unavailable, failed or invalid reranking now takes the full lexical-weighted fallback, score adjustments run once, and the cross-encoder floor/trace apply only to valid scoring. Five new regression cases and 44 existing retrieval/code cases passed. The remaining recommendations depend on the coordinated hardware/UI changes or subsequent evaluation.

## Evaluate before changing defaults

- Compare current no-reranker hybrid retrieval with reranking on hardware that can support it. Separate German/English, cross-language, exact identifiers, ambiguous follow-ups, multi-document questions and questions with no source answer. Measure **post-context-packing** evidence coverage and citation support, not only retrieval ranks.
- Time cold and warm queries separately: model load/swap, query embedding, retrieval, reranking, prompt evaluation and first token. Track peak VRAM, cancellation latency and failed loads. A fast ranking pass is immaterial if it introduces a long model swap.
- Keep the existing chunk sizes initially. Sweep a small number of sizes on representative PDFs and code before changing defaults. Larger chunks can preserve context but increase embedding/prompt work; aggressive leading truncation can discard the actual answer.
- Test whole-document expansion and document-diversity behavior against short, multi-topic documents. More supplied text is not automatically more useful. Published long-context experiments found sensitivity to where evidence appears; this motivates focused context and local evaluation, not a claim about the precise models installed here. [Lost in the Middle, original paper](https://aclanthology.org/2024.tacl-1.9/).
- Keep document-summary prefiltering and dynamic-K opt-in until recall is measured. Defer GraphRAG, LLM-generated chunk context, another vector database, a new embedding family and multi-vector indexing. Each adds ingestion/runtime/storage cost or a migration obligation without evidence that it fixes this user's current bottleneck.
- Add a fusion permutation check before a later retrieval refactor: `fuseRrf` caps the running pool after each arm. Trimming between arms can discard partial scores before later lists arrive, making the bounded approximation order-sensitive. Accumulating all bounded arm contributions then taking one final cap is worth evaluating; it is outside the immediate hardware/UI patch.

Acceptance for a later RAG tuning change: publish the corpus/model/quantization/context settings, comparable cold and warm timings, retrieval coverage, source-supported answers and uncertainty/no-answer behavior. Claim improvement only on the evaluated workload, not a universal “best RAG”.
