### Quantized KV fallback-estimator defect under investigation

A metadata-only probe of the installed SDK finds a separate reproducible arithmetic defect. Its JavaScript KV estimator multiplies scalar counts by GGML's bytes per quantization block, without dividing by values per block. Q8_0 uses 34 bytes per 32 values (1.0625 bytes per scalar), and Q4_0 uses 18 per 32 (0.5625); F16 uses two bytes per value. Consequently, the probe incorrectly estimates Q8 as much larger than F16. At 14 GPU layers, 8192 context tokens and batch 254, it estimates context VRAM at 2,557,519,501 bytes for Q8 versus 410,035,853 for F16. These are erroneous heuristic outputs, not actual allocation measurements. The probe initializes no inference backend, loads no weights and creates no context.

The installed native addon exposes block size and type size separately; the same SDK already uses both in tensor-size calculations. Its preferred V2 context estimator falls back to this JavaScript method when native simulation fails, so the deprecated method remains relevant. The [upstream KV calculation](https://github.com/withcatai/node-llama-cpp/blob/master/src/gguf/insights/GgufInsights.ts) also contains the missing conversion at review time. A minimal local patch and synthetic regressions are being prepared independently; neither installed dependencies nor the frozen BE runtime have been changed. Current observations do not establish that this fallback ran during BD, caused the 14-layer choice, or will yield a measured speedup when corrected.
